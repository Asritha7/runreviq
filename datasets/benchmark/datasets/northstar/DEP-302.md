# Release rollback decision

Fictional benchmark only. No real infrastructure or customer data.

## Situation

A fictional Harbor release is followed by a sustained error-rate increase. Compare the failure start time with the rollout timeline and with unrelated dependency changes. Temporal proximity alone does not prove that the release caused the incident.

## Investigation

Before rollback, check database schema compatibility, migration reversibility and whether old binaries can read records written by the new release. Review the last known healthy artifact identifier and the release owner decision. Do not assume every deployment is reversible.

## Controlled response

If compatibility is confirmed, obtain release-owner approval and roll back a limited group before widening the change. Watch request errors, latency and data validation checks. Stop if old binaries reject newly written records or recovery indicators worsen.

## Verification

After recovery, retain both release identifiers and a timeline for review. A rollback that reduces errors is evidence for investigation, not a complete root-cause explanation. Irreversible schema changes require a separate recovery plan.
