# Database connection pool exhaustion

Fictional benchmark only. No real infrastructure or customer data.

## Situation

The fictional Ledger API reports connection acquisition timeouts while database CPU remains moderate. Determine whether the application is waiting for a connection or whether an already running statement is slow. Keep incident timestamps and pool limits with the investigation.

## Investigation

Inspect active, idle and waiting connection counts in the application pool. Compare the pool limit with the database connection budget across all replicas. Look for transactions that hold a connection after their request has finished.

## Controlled response

Reduce admitted request concurrency with incident-lead approval while the owner investigates leaked connections. Increasing every replica pool can exhaust the database globally. Capture the oldest transaction age and its owning component before any intervention.

## Verification

Recovery requires the wait queue to drain and connection acquisition latency to return to the service target. If connections are available but queries wait on locks, use the transaction lock investigation instead of raising pool capacity.
