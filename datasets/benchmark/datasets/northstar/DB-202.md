# Transaction lock investigation

Fictional benchmark only. No real infrastructure or customer data.

## Situation

The fictional Ledger database has rising query latency without high CPU utilization. Confirm that the wait event is a transaction lock rather than storage latency or a connection acquisition timeout. Record the affected relation and the time the delay began.

## Investigation

Find the blocking transaction and list its waiting transactions. Capture transaction age, owning application and operation type using redacted query summaries. Check whether a deployment introduced a long schema migration or an abandoned transaction.

## Controlled response

Ask the database owner to approve cancellation of the identified blocker only after checking rollback impact. Killing all database sessions can cause a larger outage. Preserve the blocking chain before cancellation so the underlying cause can be reviewed.

## Verification

After the approved cancellation, verify that waiting transactions progress and no replacement blocker appears. A short-lived decrease in latency alone is not proof of recovery. This procedure does not authorize changing database durability settings.
